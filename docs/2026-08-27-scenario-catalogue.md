# vf-agentics — intention and scenario catalogue

Produced 2026-08-27 by `/vf-agentics:investigate` (run `wf_65c6093a-746`, report mode,
intelligence `max`). Survey coverage was **complete** — no dropped topics, no incomplete
or failed channels; the closing section of the report lists the gaps the catalogue
itself inherits. This document seeds the adversarial per-scenario probe (pass 2): one
analyst per scenario cluster, each judging against the requirements below.

## Main requirements (evaluation rubric)

Stated by the user 2026-08-27. Every proposed improvement must serve at least one.

1. **Configurable intelligence per task.** Intelligence level is balanced and
   configurable at task granularity — not one dial for the whole run.
2. **Completion is mandatory.** If a task is set, it must be done, regardless of cost.
   Cost is never a reason to stop, truncate, or silently drop work.
3. **Minimize cost within the chosen level.** Given the selected intelligence level,
   any available cost reduction must be taken. Cheap where cheap suffices.
4. **Judge the effort's shape.** Development tasks differ: some need strict
   red-green-refactor TDD, some are simple tasks, some are in between. The system must
   judge which shape a piece of work needs. Applies mostly to work orders.
5. **Maximum resumability.** Detect early when a session limit is likely to be hit —
   never start lengthy work that is doomed to be killed; split it into smaller steps.
6. **Deterministic → script.** If something is deterministic, it must be done as a
   script, not a model. Model calls are reserved for judgment.

## Observed incidents (live evidence from this investigation, 2026-08-27)

- **Session restart killed the in-flight vfa-investigate workflow.** Its journal
  recorded 11 agents `started`, 0 `completed` — partial agent transcripts existed but
  nothing was salvageable through the resume cache. Direct hit on requirement 5.
- **Resume dropped the workflow args.** Relaunching via `scriptPath` +
  `resumeFromRunId` runs the script argless; it received `question: ""` and returned an
  empty coverage-honest result in 5 ms. The script's guard is good; the resume path
  silently losing the question is not, and skills/investigate/SKILL.md records the
  runId without warning that args must be re-passed on resume.
- **A usage limit killed all 16 probe analysts mid-flight.** The account's session

  tokens spent with zero completed agents to cache. The coverage block honestly
  reported every scenario unprobed — but nothing predicted the limit before dispatch,
  and no partial work survived. Requirement 5's early-detection clause, exactly.

## Intention

vf-agentics is a pool of delivery skills (design → plan → programme → develop, with investigate/probe/runs/find-existing-solutions alongside) sharing one agent pool and one evidence core (vfa-survey), governed by a single IRON LAW: a set task must be done and finished no matter the cost — efficiency is an optimization, never a termination condition (docs/superpowers/specs/2026-08-08-vf-agentics-design.md §0). The one failure mode the whole plugin exists to prevent is **a partial result indistinguishable from a whole one**. Everything below is a mechanical consequence of that: no counter-based termination anywhere (lint-enforced), verdicts and completeness derived in JS from recorded facts and never self-reported by a model, every exit path returning a coverage block `{complete, dropped, incomplete, failed_channels, unreached, resumable}` where `complete` is computed as the AND of the four loss arrays being empty, and every degradation landing in exactly one named array plus prose instead of vanishing or throwing.

Note before the catalogue: **survey is not a user-facing skill.** No skills/survey/SKILL.md exists; workflows/vfa-survey.workflow.js is the shared evidence core reached through design Step 1 (skills/design/SKILL.md:28) and nested inside investigate, develop, find-existing-solutions, and diagnose.

## A. Survey core (shared evidence engine — workflows/vfa-survey.workflow.js)

**A1. Happy path.** Trigger: any consuming pipeline supplies a question. Behavior: planner emits topics (+ optional common_ground, history flag, docs flag) → one scout per topic plus a common-ground scout run to exhaustion → historian/doc-researcher side channels if flagged → one analyst per topic writes a verdict; coverage derived in JS at :244-257.

**A2. Empty question.** Trigger: blank/whitespace question. Behavior: immediate empty return, nothing dispatched, `unreached` says so. Source: :269-272.

**A3. Planner death or zero topics.** Trigger: planner throws (`.catch→null`) or returns no topics. Behavior: empty result, `unreached: ['planning produced no topics, so nothing was searched']`. Source: :310-318.

**A3b. Prior context (increment 25).** Trigger: caller passes `prior` — an effort's stored survey. Behavior: it reaches the PLANNER prompt and nothing else (no scout, no analyst, no gate), framed as unverified notes that may aim the decomposition and may never retire a topic; every topic is still searched; it appears in LAUNCH_ARGS so a resume re-passes it. Source: workflow.js prior block; test/vfa-survey-scenarios.test.mjs (prior context).

**A3c. Absence deposit (increment 25).** Trigger: a topic with a non-empty `kb_path` whose scout EXHAUSTED its search and found zero hits. Behavior: one `kb-deposit` dispatch mints `absence:` + fnv1a(path + key) — id from stable inputs, the scout's `no_match` in the prose so a rewording SHADOWS rather than piles up — with `observed_at: 'HEAD'` resolved by the writer in the repository; a search that stopped short, or found anything, or named no subtree deposits NOTHING. Source: workflow.js absenceDeposits/absencePrompt; lib/kb.mjs OBSERVED_AT_HEAD; test (absence deposits).

**A3d. Deposit does not land.** Trigger: the writer refuses, or the shell truncates. Behavior: logged, a `from_kb` line saying the next run pays for the same empty searches again, and `coverage.complete` UNAFFECTED — a deposit is written for the NEXT run and costs this result nothing. Source: workflow.js deposit block; test.

**A4. Planner topic overflow.** Trigger: plan exceeds maxTopics(8). Behavior: logged only — ALL topics are still searched; cost is controlled by method, never by dropping work (IRON LAW §8). Source: :320-327.

**A5. Pre-0.16 plan without common_ground.** Trigger: resumed older plan. Behavior: degrades to "no shared ground," never throws. Source: :329-332; commit bc58c9f.

**A6. Resume-to-exhaustion engine (all evidence agents).** Trigger: any scout/historian/doc-researcher round ends. Behavior: the only exits are goal-shaped — `exhausted`; a thrown round (work kept, exhausted:false); a null/empty round; a dead end (`stop_reason!=='exhausted'` but blank not_reached — "another round would launder it into completeness"); or `stuck` (a round that gained no new dedup keys). No round counter exists anywhere. Source: :353-393; the "no budget stops" postmortem, commit df56404 (0.12.0).

**A7. Scout resumed, ends unexhausted.** Trigger: scout stops unfinished. Behavior: resume prompt feeds back ALREADY SEARCHED / ALREADY FOUND / STILL NOT REACHED (never restart, agents/scout.md:42); if it still ends unexhausted its topic key joins `partial[]` → `incomplete`. Source: :531-552.

**A8. Side channel requested but questionless.** Trigger: planner sets history/docs flag true but produces no question. Behavior: `{requested:true, result:null, error:'the planner marked it necessary and then produced no question'}` — the once-invisible bug case made loud. Source: :402-428.

**A9. Side channel returns falsy or throws.** Trigger: historian/doc-researcher dies or returns nothing. Behavior: caught, logged, channel joins `failed_channels`; failed history means "any claim about when/why is unsupported" in downstream prose. Source: :407-428, :638-640.

**A10. Channel truncated.** Trigger: channel returned but `stop_reason!=='exhausted'`. Behavior: joins `incomplete` (a different claim than failed), and a "COVERAGE LIMIT — never reached:" caveat is appended to its findings string. Source: :646-675.

**A11. Common-ground scout unfinished.** Trigger: shared-ground search didn't finish. Behavior: its hits plus a WARNING injected into every analyst prompt; other scouts were told to skip that ground. Source: :527-529, :560-580.

**A12. Analyst death.** Trigger: per-topic analyst throws (`.catch→null`). Behavior: reconciliation is by pipeline INDEX, not echoed topic string — the missing finding drops the topic key into `dropped`. Survey never throws. Source: :587-627.

**A13. Coverage schema deadlock (fixed).** Trigger: exhausted agent with nothing to report omits a required coverage field. Behavior: only the payload field is schema-required; coverage fields are demanded by charter prose ("always include, empty string never omit") and normalized in JS. Source: :78, :140; agents/scout.md:36, historian.md:52, doc-researcher.md:25; commit 7a447b9 (0.12.1).

**C22. Top-level crash.** Trigger: anything escaping every guard. Behavior: the catch still returns developResult() with complete=false and failed_channels:['pipeline'] — no path ends in an uncaught throw. Source: workflow.js:4263.

**C23. Triage decline.** Trigger: fresh (non-resume, non-plan-only) change carrying all three properties — one obvious locus, a settled shape, nothing to partition. Behavior: the skill offers the work back before any survey is bought — "this fits a direct session with a reviewer pass; the pipeline would cost more than it protects" — with the audit numbers as the rationale (7 of 10 sessions better served direct; ~400–500k survey tokens per run; 10–12 dispatches per TDD'd behavior) and a named direct path that keeps the parts that paid: a fresh adversarial reviewer over the diff, and a failing test first where the change is a fix. A decline is a recommendation with data, never a refusal, and the skill declines nothing when any of the three properties is absent. **C24. Triage override.** Trigger: the user answers "run it anyway" to a decline. Behavior: the run proceeds at step 1 unchanged, and the skill says nothing further about cost — one recommendation, not a negotiation. A second round of argument would convert advice into a gate, which is a cost-shaped termination condition the IRON LAW does not permit any more here than anywhere else. Source: skills/develop/SKILL.md, same section; IRON LAW §0.

**C25. Courier verify (the happy path).** Trigger: any order verification, any fix round's re-verification, any wave's merged head. Behavior: the dispatch names ONE `lib/verify.mjs` invocation — worktree, base..head, every locus path, the run's established commands base64-encoded, and the journal flags — and the verifier's whole job is pasting its stdout into `payload_raw`. The workflow recomputes the payload's own FNV-1a digest over what arrived before reading a field of it, then computes the verdict with the same predicates as ever. One dispatch, at haiku, and its tier does not move with the intelligence dial: pasting one line is pasting one line. The program writes the run's `verify-observed` line itself, inside the process that measured, so the courier journals nothing and no second dispatch records anything. At the merged head the same courier runs `--mode integration` — build and suite only, both other arrays honestly empty, no journal flags. Source: workflows/vfa-develop.workflow.js `verifierPrompt` / `measureOrder` / `measureWave`; lib/verify.mjs; docs/superpowers/specs/2026-08-30-increment-11-contracts.md §1–§2; test/vfa-develop-verify-courier.test.mjs.

**C26. Typed-error escalation.** Trigger: a whole, correctly digested payload whose `error` is non-null — `command_unknown` (nobody has established this repository's build/suite/single-test commands), `series_unreadable`, `test_unrunnable`, `tree_not_restored`, `suite_failures_unnamed`, `shell_refused`, `base_checkout_refused`, `main_worktree`, `no_worktree`. Behavior: no second courier — a payload that arrived whole and said no is not a transcription defect — and the verifier is dispatched in investigate mode instead, carrying the runner's own words plus the hand-run procedure its charter holds. Its result is the same VERIFY facts, plus `commands`: what it establishes is adopted for every later check in the invocation and copied out to the run's `knowledge` set, and is never read back out of it (a coder's guessed command must not become a measurement's command). The escalation is not a way out of a verdict — an investigator reporting a broken environment produces findings, a fix round, and an escalation when nothing moves. Source: agents/verifier.md investigate mode; workflow.js `verifierInvestigatePrompt` / `adoptCommands`; contracts §2c, §3.

**C27. Digest-mismatch refetch.** Trigger: the measurement does not survive the trip — the courier returned nothing, `stop_reason: 'failed'`, unparseable `payload_raw`, an envelope missing its digest, or a payload that digests to something other than what it carries. Behavior: exactly ONE refetch, one tier up (haiku → the verifier's frontmatter tier), logged as "did not survive the trip"; a healed measurement carries on as though nothing happened and the order is NOT escalated, because the work was never in question. Two damaged copies escalate the order with reason `verify_untransportable`, naming the transport rather than the work, and no fix round is bought — a coder would be sent at a defect nobody observed. At the merged head the same exhaustion stops the line, which is what a failed wave-verify dispatch always did. Two rungs, never a loop: a third courier types into the same shell as the second. Source: workflow.js `carriedVerify`; contracts §4; the same ladder as D-series resume transport.

**C28. Fresh-entry seeding from the knowledge base.** Trigger: a plan with at least one declared locus, in a repository holding `.claude/vfa/kb/`. Behavior: ONE `kb-chain` dispatch — `vf-agentics:kb` at haiku — before the first order is dispatched, over every locus path in the plan; the chains are independent of anything a wave does, so buying them per order would buy the same courier N times. The workflow recomputes the payload's own FNV-1a digest before reading a field of it. Each coder dispatch (first series, continuation, and fix round) is then seeded from ITS OWN locus chain with the **fresh** entries only, under the existing "observations, not instructions; verify before relying" wording. Stale entries ride nothing — a lead is worth a look when somebody is going looking, and worth nothing to a coder mid-order; orphaned entries are about ground that is gone. Verify dispatches carry no entry at all, fresh or otherwise, which is the run-`knowledge` asymmetry unchanged: a coder may act on hearsay and be caught by verification, and verification has nothing behind it. The single exception is `command`-kind entries, which reach the check runner as `--build-b64` / `--suite-b64` arguments rather than as prose, and only when the entry is fresh AND `source.via === 'verify-established'` — a coder's report can enter the base as a claim, never wearing the source that says a measurement established it. A base that cannot be read leaves `failed_channels: ['kb']` and `complete` untouched: it is advisory, and nothing is verified on it. Source: workflows/vfa-develop.workflow.js `kbChainPrompt` / `kbFor` / `knowledgeSection` / `adoptKbCommands`; agents/kb.md chain mode; lib/kb.mjs `chain`; docs/superpowers/specs/2026-08-30-increment-13-contracts.md §6–§7; test/vfa-develop-kb.test.mjs.

**C29. Hand-commit demotion.** Trigger: any read of an entry (`kb chain` or `kb verify`) after a commit touched the ground that entry is about — made by a person in a direct session, by another tool, or by this pipeline; the base records no distinction and needs none. Behavior: `git log <observed_at>..HEAD -- <about>` is non-empty, so the event shortcut is not taken and the entry falls to the digest check over its file anchors; a moved anchor reads **stale** and the entry stops being evidence and becomes a lead. A commit that touched the subject and left it byte-identical passes the digest check and stays fresh — non-empty demotes, it does not condemn. A commit elsewhere in the repository changes nothing, because the arithmetic is over the entry's own subject. Uncommitted edits are covered separately: one `git status --porcelain` per invocation names the moved paths, and an entry whose subject overlaps one skips the shortcut, because an unobserved change must never read as no change. This is the case that ruled out keying invalidation to the run ledger: a hand commit writes no ledger line, so ledger arithmetic would have certified the entry fresh. Source: lib/kb.mjs `stateOf` / `freshByEvent` / `dirtyPaths`; docs/2026-08-30-proposal-hierarchical-knowledge-base.md §3a (amended in place); contracts §3; test/kb.test.mjs, the fixture where nothing in the repository has ever recorded a run.

**C30. Write-back at run end.** Trigger: a run reaching its end with at least one approved order carrying a `discovered` entry, or with a build/suite/single-test command a verification established this invocation. Behavior: ONE `kb-write` dispatch at the seam after the integration review — the batch minted whole, digested, and carried base64 on one argv slot, with `lib/kb.mjs append` recomputing the digest and refusing the WHOLE batch on a mismatch or on any malformed member. Approved orders' discoveries become `gotcha` entries whose `about` is that order's declared locus; escalated orders' discoveries stay out, inherited rather than restated, since `implemented` is exactly the approved set. Established commands become `command` entries with `source.via: 'verify-established'`, about the repository's root manifests — the durable half of increment 11's escalation, so the next run stops re-buying the investigator. `observed_at` is the run's base sha. Ids are deterministic (`gotcha:<fnv1a of the claim>`, `command:<name>`), which is what makes newest-id-wins shadow a re-observation instead of accumulating duplicates. The destination node is computed from `about` and never passed, and the file anchors are measured by the program in the repository — a caller with no filesystem supplying a digest would be supplying a claim wearing a measurement's shape. A deposit that cannot be written is reported and lands in `failed_channels`; `complete` is untouched, because the run did the work and what failed is the record of what it learned while doing it. Source: workflow.js `kbDeposits` / `kbDepositPrompt`; agents/kb.md deposit mode; lib/kb.mjs `appendEntries`; contracts §5, §7d–§7e; test/vfa-develop-kb.test.mjs.

**C31. A verification topic, not a rediscovery.** Trigger: a survey whose planner named a `kb_path` for a topic, where the chain at that subtree holds at least one **fresh** entry. Behavior: before the decomposition, ONE `kb-index` dispatch — `vf-agentics:kb` at haiku — reports which nodes hold entries, how many, and of which kinds, and NO state at all; the planner decomposes against that list and names each topic's subtree. After the decomposition, ONE `kb-chain` dispatch covers every named subtree at once, and the workflow recomputes the payload's own FNV-1a digest before reading a field of it. The order is the correction the probe forced: before a decomposition exists the only known paths are the roots, and a chain at a root is the repository-wide node alone, so "chains at the roots" would reach almost nothing. The topic's scout is then told the fresh entries are EVIDENCE and that its job is verification — confirm the locations they name still exist, spend the rest of the pass on what they do not cover, and report an entry that turns out wrong in `no_match` as the finding it is. The topic's analyst receives the same entries as CACHED evidence with the instruction to say "from the knowledge base, observed at <commit>" where a conclusion rests on one. `coverage.from_kb` gains a line naming the topic, how many entries, the subtree and the commits. Source: workflows/vfa-survey.workflow.js `indexSection` / `kbForTopic` / `cachedEvidenceSection`; agents/kb.md read mode; lib/kb.mjs `index`; docs/superpowers/specs/2026-08-30-increment-14-contracts.md §1–§3; test/vfa-survey-scenarios.test.mjs.

**C32. A stale entry is a lead, and reaches the search only.** Trigger: the chain at a topic's subtree holds entries the program computed as `stale` (the ground moved since they were observed) or `orphaned`. Behavior: stale entries reach that topic's SCOUT under a LEADS heading — places to look, never facts to report, with "never report a location you have not seen for yourself" — and reach no analyst at all, because an analyst judges what was found and a claim it cannot check does not belong beside locations it can. Orphaned entries reach nobody: their ground is gone. No `from_kb` line is written for a topic that received only leads, since no verdict rests on one and claiming provenance for it would make the field mean less. The topic is searched in full, exactly as it would have been without the base. Source: workflows/vfa-survey.workflow.js `kbForTopic` / the scout's `kbBrief`; contracts §2–§3; test/vfa-survey-scenarios.test.mjs.

**C33. The null survey, and the stale chain that refuses it.** Trigger: `vf-agentics:vfa-develop` invoked with BOTH `settled_shape: true` (the caller's judgment that the approach is decided rather than something the change must discover) and a non-empty `ground` (the paths the caller says the change is about). Behavior: ONE `kb-ground` chain read over the named paths, before the nested survey. The survey phase collapses to nothing — no `vfa-survey` invocation at all — only if EVERY named path carries at least one `fresh` entry; the chain then becomes the run's evidence base, handed to the planner as recalled-not-searched ("It is not a search: anything this change needs that these entries do not name was not looked for by anybody"), and `coverage.from_kb` carries the whole account: that no survey ran, that nothing was re-searched, which paths were covered and at which commits. `complete` stays true — nothing was dropped or left unreached — and what makes that honest rather than laundering is that `from_kb` makes a recalled result distinguishable from a searched one. Three refusals, each by construction: a chain whose entries are all stale (a lead is not evidence, so a null survey on a stale chain is unreachable rather than merely discouraged), one uncovered path among several (the ground is what the caller named, all of it), and a chain that could not be read ("I could not ask" is not "the answer is yes"). Each refusal names the path and reason in the log and runs the full survey. Either input alone does nothing. Inside the survey, the same rule at topic grain: when every topic rested on fresh ground, the coverage block says what ran was a verification pass rather than a discovery survey. Source: workflows/vfa-develop.workflow.js the null-survey seam / `coverageOf`; docs/design.md "Phase presence, derived"; contracts §4; test/vfa-develop-kb.test.mjs.

**C34. Fix-round tier escalation.** Trigger: a review round of 2 or higher dispatching a fix — that is, a round whose predecessor's fix did not clear its blockers. Behavior: the fix implements at the opus floor, `higherOf(base, 'opus')`, because a fix that failed to clear is *measurement* that the tier was too low rather than a prediction that it might be. One step: round 3 and later find the tier already moved. The rise is licensed above the run's ceiling at `low` and `normal` — the single deliberate exception to "the dial is a ceiling nothing may exceed" — and it is licensed by an observed failure, never by an agent's opinion of its own work, which is the property the downward-only `weight` rule protects. Every other coder dispatch (first series, continuation, coupled orders) passes no round and prices exactly as before. It is **not** an exit and adds none: the loop's three computed exits are unchanged, so the pathological-alternation gap below is neither closed nor widened by it — what changes during such a loop is which brain is implementing. The round that moves the tier logs it, comparing the resolved tier against the prior round's rather than a hardcoded round number, and stays silent at `max` where nothing moved. Source: workflows/vfa-develop.workflow.js `coderFor`, the review loop's fix dispatch; docs/superpowers/specs/2026-08-30-increment-20-contracts.md §2; docs/2026-08-17-intelligence-tiering.md §6 ruling 4 (the "later, measured" fix-round escalation, landing here); test/vfa-develop-model-tiering.test.mjs.

**C35. The floors escalation may not cross.** Trigger: any tier resolution. Behavior: four bounds, each computed. The escalation never exceeds opus — at `--intelligence=max` the coder base is already opus and `higherOf` returns it, never fable, because the field praise the coder tier rests on was of Opus as implementer (tiering §7). A `light` order loses its discount the moment it is proven hard: `structural || proven` is tested before `weightOf`, so the cheap tier cannot survive its own failure. `outputIsTheYardstick` — a red order or a contract order — floors at opus at every dial position and is waived nowhere, because everything downstream is fenced to that output and has no standing to contradict it. And **no judge escalates at all**: `judgeFor` is unchanged, `weight` still moves it downward only, and a reviewer that got stronger because its own earlier rounds found nothing would be a reviewer whose tier is set by its own output. A cheaper judge does not refuse less often because the work turned out easy — it refuses less often full stop, and the run still goes green. Source: workflow.js `coderFor` / `judgeFor` / `outputIsTheYardstick`; contracts §1–§3; docs/design.md "Model tier, earned"; test/vfa-develop-model-tiering.test.mjs.

**C36. What the tier bought, recorded.** Trigger: any order whose review loop closes with an empty open set. Behavior: the `order-approved` state line carries four additive fields beside the ones it always had — `weight` (normalized, so a plan written before the field existed records `standard`, which is what it was priced at), `coder_model` and `judge_model` (the order's **base** tiers, `'charter'` where the run named no model, because writing the charter's current default into a durable record would state as fact something a later edit to the agent's frontmatter silently falsifies), and `review_rounds`. The escalated tier is not stored and does not need to be: `review_rounds >= 2` is exactly the condition C34 escalates on, so it is derivable while the decision the run made up front stays legible. Additive only; `escalationLine` and `waveLine` untouched; every surviving reader selects by name and `lib/ledger.mjs` is a transport check rather than a schema, so the new fields ride the same digest as the old ones. Alongside it, the plan-size log gains the weight distribution (`Weights: 2 light / 11 standard / 1 heavy.`) counted through the same `weightOf` that prices it, and the planner prompt gains the fact that somebody watches the answer — a plan whose orders are all one weight is now visible before the first dispatch rather than inferable from the invoice. No `weight_reason` field was added: a required field on `WORK_ORDER_ITEM` changes what every resumed plan must carry, for a justification nothing can check (A13, the coverage deadlock, is the same shape). Nothing reads the record back — a pipeline re-tiering future orders from its own past outcomes would be setting its own price from its own output. Source: workflow.js `orderLine` and the plan-size log; contracts §4–§5 (extending increment-6-contracts.md §2, whose copy table this increment corrects: three of its eight listed copies no longer exist); test/vfa-develop-model-tiering.test.mjs.

**C37. A regression net, and the question the discriminator may not ask it.** Trigger: a work order carrying `pins: 'data'` — the planner's statement that its tests exist to hold something already correct in place (the shipped bundle is still valid, the generated file still matches its source) rather than to pin a change. Behavior: `discriminates` drops the `failed_on_base` conjunct for that order and keeps `passes_now`, so the waiver is one conjunct wide: a data-pinning test that does not actually pass still fails the order. `pinsData` is gated on `role: 'none'`, which makes the marker inert on a red order rather than trusted there — a red test must fail at base, the opposite claim, and a contradiction is made harmless at the accessor instead of downstream. The field is required on `WORK_ORDER_ITEM` for the reason `role` and `weight` are, and normalized to `'behaviour'` on read so a plan written before it existed resumes under the verdict it was planned under. `lib/run-verdict.mjs` carries the same two functions, so a resume derives the same pass the live run did. The planner is told to write the mutation that DOES check such a test — delete this field, duplicate that id, and which case must fail — into the acceptance criteria, and the coder is told to run it by hand and report what it saw, because nothing mechanical downstream runs it. Field case: run `20260902-124933`'s `real-bundle-tests` was correct, had the right check written in prose, and had no field in which to say so. Source: workflow.js `pinsData` / `discriminates` / `plainVerifyOk` / `roleSection`; lib/run-verdict.mjs; agents/planner.md §5c; test/vfa-develop-pins-data.test.mjs.

**C38. The fix round nobody can win.** Trigger: a `role: 'none'` order that fails verification where the discriminator is the ONLY failing fact — computed as `!verifyOk(v, wo) && verifyOk({...v, discriminator: []}, wo)`, which asks "would this have passed if the discriminator had asked nothing?" rather than parsing finding ids. Behavior: escalate immediately, reason `discriminator_undecidable`, with no fix round dispatched at all; the escalation carries the discriminator's own findings plus the order's acceptance criteria quoted verbatim and a note that the plan should have marked it `pins: 'data'`. The order still does not merge — the gate holds and a person rules on it — but the verdict names the right question and costs one round rather than two. Narrowed to `role: 'none'` deliberately: a red order's discriminator failure is its work and a fix round can move it, and a refactor's empty discriminator is a requirement rather than a waiver, so reading either through this predicate would short-circuit an order a coder could genuinely fix. A discriminator failure standing beside a failing suite or a blocking series finding still buys its round. Field case: the same order took two rounds and a human override, and the second escalation read `verify_failed_repeatedly` — a wrong-question verdict restated more confidently. Source: workflow.js `discriminatorUndecidable` / `criteriaEvidence` / `verifyUntilGreen`; test/vfa-develop-pins-data.test.mjs.

**C39. An integration review over a tree that is not the whole change.** Trigger: the integration review running when some planned order did not merge — escalated, blocked, withheld or deferred. Behavior: the reviewer's dispatch names every missing order with its title under a `THIS IS A PARTIAL MERGE` heading, and is told to reason about the incompleteness out loud — where a finding depends on what is missing, say which order in its evidence — rather than to drop the finding or to review the tree as though it were whole. Every critical the review reports then reaches `coverage.unreached` with the same caveat attached, so a person acting on a finding sees the tree it was made against. A whole merge carries no caveat at all, because a warning that is always present is a warning nobody reads. Field case: run `20260902-124933` produced an integration finding whose correct fix ran OPPOSITE to the one proposed, because two coupled orders were still outstanding; the finding was accurate about the state it saw. Source: workflow.js `integrationReviewPrompt` and the integration-review seam; test/vfa-develop-partial-merge.test.mjs.

**C40. Worktree paths come from `roots`, never from a cwd.** Trigger: any worktree this run creates — the per-order trees and the integration tree. Behavior: the path is interpolated from `primaryRoot()` (`worktreeDir()`), so the dispatch names where the tree goes instead of leaving it to whatever directory the agent's shell inherited; both prompts, and `agents/verifier.md`, additionally tell the agent to enter the repository and confirm with `git rev-parse --show-toplevel` before creating anything, which closes the case where `roots` is itself `'.'`. Field case: a retry invocation in run `20260902-124933` created `…/worktrees/vf-agentics-develop-8a30f0/.claude/worktrees/vfa-real-bundle-tests` — nested inside the ORCHESTRATING session's worktree, because the relative path resolved against that session's Bash cwd. The run's recorded `roots` was correct throughout; nothing was reading it here. Source: workflow.js `primaryRoot` / `worktreeDir` / `worktreePrompt` / `setupPrompt`; agents/verifier.md.

**C41. The typecheck, asked apart from the suite.** Trigger: every order verification and every wave verification, in any repository. Behavior: `lib/verify.mjs` runs a third named command between the build and the suite and records `typecheck` as `passed` / `failed` / `absent` under the same rules as the other two — never inferred, `absent` only where somebody declared it, its failure output carried in `notes` under a `typecheck output tail:` heading rather than in a field of its own. `verifiable` and `waveVerifyOk` gain one conjunct beside the build's, and `verifyFailureFindings` raises `<id>-typecheck` separately so a fix round is not sent after a build that works. `absent` is the ordinary answer and costs nothing: it produces no finding, no escalation, and no entry in `measured` — the same asymmetry the build has, so an order with nothing mechanically checked still reports the emptiness IRON LAW §4 exists to surface. An unnamed typecheck escalates `command_unknown` exactly as an unnamed build does, which buys no extra dispatch because the first verification in a run already escalates for the build; the investigator is charged to name it, told that most repositories have none and that absent is the right answer there, and told why the suite cannot be read for it. Field case: an order's branch tip carried 826 passing tests over a tree `tsc --noEmit` rejected — esbuild strips types without checking them — and the branch was left at a literal `Revert` commit with a broken build. Source: lib/verify.mjs; workflow.js `VERIFY` / `verifiable` / `waveVerifyOk` / `verifyFailureFindings` / `adoptCommands` / `verifyInvocation`; lib/run-verdict.mjs; agents/verifier.md step 3; test/vfa-develop-typecheck.test.mjs; test/verify.test.mjs.

**C42. A journal line from before a field existed.** Trigger: a resume reading a `verify-observed` line written by an older version, which carries no `typecheck` key at all. Behavior: `parseJournal` normalizes the missing key to `'absent'` — the honest reading, since that run never asked the question — and deliberately leaves it out of the `recorded` predicate, so an older line is a whole record of what its version measured rather than a torn one. A run planned under the old verdict therefore resumes under the old verdict, which is the same rule `pins` follows. Source: lib/run-verdict.mjs `parseJournal`; test/run-verdict.test.mjs.

**C43. What the coder discovered reaches the reviewer.** Trigger: every per-order review round. Behavior: `reviewerPrompt` receives `discovered` alongside `concerns`, under a charge naming what to do with it — most of it is knowledge-base material and none of the reviewer's business, and the reason to read it anyway is the one entry that names a decision the order had to make and did not resolve, which is ruled on like any other finding. The section is shown even when empty, so its emptiness is legible. Deliberately NOT a third typed channel: `agents/coder.md` already charges `concerns` correctly and the workflow already routed it, so the field case was a misfiled note rather than a missing channel, and a third bucket would be a third place for the same confusion to land. Field case: a coder wrote a stage-blocking defect into `discovered` with both remedies named, and because the channel's only consumer was the run-end knowledge deposit it cleared three green gates and surfaced at the integration review. Source: workflow.js `reviewerPrompt`; agents/reviewer.md §4; test/vfa-develop-typecheck.test.mjs.

**C44. A repository with no knowledge base at all.** Trigger: any chain or index read where `.claude/vfa/kb/` does not exist. Behavior: `kbPresent` is computed on every read like every other state here and reported as `kb_present`, and both `notes` say so in as many words. The develop workflow's null-survey refusal branches on it: no base is a setup fact — the collapse cannot fire in that repository for any change, on any day — while a stale chain is a base doing its job on a day the ground moved, and the stale wording gains "though the base exists" so neither can be read as the other. Without the split both arrive at a caller identically as an empty chain, and a project that has never had a base reads every refusal as routine staleness while paying for a full survey every run. Field case: this plugin's own repository has no base and never has, and the report that found it read the refusal as ordinary. Source: lib/kb.mjs `kbPresent` / `chainFor` / `indexTree`; workflow.js null-survey refusal; test/vfa-develop-kb.test.mjs.

**C45. A journal heredoc a guard will not pass.** Trigger: an agent appending its own `journal.jsonl` line where a permission layer in front of Bash refuses a multi-line command as too complex to verify. Behavior: the dispatch and `agents/verifier.md` both name the fallback — write the same JSON to a scratch file inside your own worktree and redirect it in, `--file journal < vfa-journal.json` — because the writer reads standard input either way, so it is the identical line by an identical route. `echo` and quoted strings stay forbidden; those are the shapes that corrupted records before. Journal lines keep the heredoc as the default, unlike state lines' base64 (increment 21 §5a), because they carry values only the observing agent knows and there is nothing to encode ahead of time. Field case: two agents in one run met the refusal independently and each invented this same workaround — nothing in the pipeline had said it was possible. Source: workflow.js `journalSection`; agents/verifier.md.

**C46. A regression net, broken on purpose.** Trigger: a work order carrying `mutations` — a text substitution in one tracked file plus the test files that must fail once it is applied. Behavior: `lib/verify.mjs` runs them last, after the discriminator has restored the tree, and per spec requires the `find` text to occur EXACTLY once, writes the substitution, runs each named test through the single-test template, reverts with `git checkout -- <file>`, and confirms the file is clean — a file still dirty afterwards is `tree_not_restored`, the same loudness the discriminator has, because a deliberate break left in a tree sends the next fix round after a defect nobody wrote. `bites` is true only when every named test was observed failing; a test that could not be LAUNCHED under the mutation is noted and not counted as failing. `mutationsBite` is one conjunct in `plainVerifyOk`, carried identically in lib/run-verdict.mjs, with its matching finding in `plainFailures`. A substitution rather than a command deliberately: a command can do anything and has no inverse, while this cannot leave the worktree and reverts with one git call. Why it exists: `pins: 'data'` waived the base question and thereby removed the ONLY mechanical question such a test was being asked, leaving `passes_now` — which a test asserting `true === true` also satisfies. Source: lib/verify.mjs `mutateAndRun`; workflow.js `mutationsBite` / `plainFailures` / `verifyInvocation`; lib/run-verdict.mjs; agents/planner.md §5c; test/verify.test.mjs; test/vfa-develop-pins-data.test.mjs.

**C47. A mutation spec the program could not apply.** Trigger: a declared mutation whose `find` occurs zero times (stale against the file), occurs several times (ambiguous about which site broke), whose file is missing or unreadable, or which names no failing test. Behavior: `applied: false` with a reason, and the order fails under a finding that names the SPEC as the defect — "fix the spec, in the plan, rather than the test" — never as a net that does not bite. The two must not collapse: a spec nothing could apply is not evidence about the test, and reading it as one is the laundering IRON LAW §2 forbids. The coder is told the same split: a non-biting net means the test is the defect, an unapplied spec means the plan is, and it goes in concerns rather than being made to fit by editing the file. Source: lib/verify.mjs `mutateAndRun`; workflow.js `plainFailures`; the `pinsData` roleSection; test/verify.test.mjs; test/vfa-develop-pins-data.test.mjs.

**C48. Fix rounds cycling between two failure states.** Trigger: a verify fix loop whose failing-fact set returns to one this order has already been in — A, B, A — which `verify_failed_repeatedly` cannot see, because it compares only with the round immediately before and the coder is moving every round. Behavior: escalate as `verify_oscillating`, naming the plan rather than the coder: two constraints on this order are in tension and no commit inside its locus satisfies both. Where a locus breach is among the failing facts the escalation says so outright and asks for the locus to be widened in the plan and the order retried, because a coder may not widen its own fence. `verify_failed_repeatedly` is unchanged and still owns the stuck-in-place case; visiting a failure state once and leaving it is what a fix round IS and never trips this. Field case: an order widened a closed union whose total records lived in other files' fixtures, its locus did not name them, and the coder cycled between a blocking locus breach and a tree that would not compile — writing the same correct row three times, reverting twice, and leaving the branch on a literal `Revert` commit. Source: workflow.js `verifyUntilGreen` `seenFailureKeys`; agents/planner.md rule 4a; test/vfa-develop-scenarios.test.mjs.

**C49. An order that widens a closed set.** Trigger: planning an order that adds a member to a union, enum, variant set or any other closed alphabet. Behavior: the planner is instructed that such an order owns every EXHAUSTIVE consumer of that set — total mappings keyed on it, switch statements with no default, arrays claiming to list every member — and that those consumers usually live in other files including test fixtures. It must search for them before declaring the locus, and where it cannot establish the full set from its evidence it declares a `blocking_gap` rather than a locus it is guessing at. Deliberately an instruction rather than a grep: `Record<Union` is TypeScript-only in a language-agnostic pipeline and is not even complete for TypeScript, missing mapped types, switch exhaustiveness and all-members constants — a search that looks complete and is not buys false confidence. The mechanical half is C48, which detects the cycle that results and names the locus as the defect. Source: agents/planner.md rule 4a.

**C50. The fix lane.** Trigger: `develop` invoked with `lane: 'fix'` and a `locus` the caller has already triaged the change down to. Behavior: the survey is skipped wholly and by declaration, and the planner is charged as a SCRIBE — one order, id W1, the caller's locus confirmed and widened where short, `deps` and `shared_files` empty, `partition_raw` written out rather than computed, at `low` effort on sonnet rather than the run's judge tier. A separate prompt rather than the decomposition prompt with a note attached, because handing a scribe eighty lines about provider ordering and wave arithmetic invites it to find work that is not there; where the change genuinely cannot be one order it says so in `blocking_gaps` and returns the order anyway, leaving the full-lane decision to the caller. It is a lane INSIDE this workflow, not a workflow of its own: worktrees, the check runner, the review loop, the ledger, the resume verdict and lib/gc.mjs are inherited entire, so the lane is resumable the day it lands. The one dispatch it keeps that it could have dropped is that planner — the only place the run directory, the plan envelope and the digest manifest are written, and a lane with no resume point pays its whole price again after a session limit. An unknown lane value falls back to `full`, never to `fix`. Evidence: a ten-session field audit found seven of ten better served by a direct session and named the adversarial review and the discriminator as what the pipeline was actually buying — and triage then ended by handing the work back, so that two-thirds got rebuilt by hand or skipped. Source: workflow.js `LANES` / `fixLane` / `plannerPrompt`'s fix branch; skills/develop/SKILL.md "The fix lane"; test/vfa-develop-fix-lane.test.mjs.

**C51. The fix lane's admission rule.** Trigger: `lane: 'fix'` with no `locus`. Behavior: refused at input, before the existing-run check and before anything at all is dispatched, with `complete: false` and a message naming the way forward — pass the files, or use the full lane and let the survey find them. What licenses skipping a survey is that the caller has already established which files the change is about, which is exactly the judgment the survey would have been bought to make; without one the alternative is a planner inventing a fence from a change string, and a fence in the wrong place is one the coder may not widen and costs the ORDER rather than the dispatch (C48 is that failure, already observed). Source: workflow.js input-refusal block, beside `base_ref`'s; test/vfa-develop-fix-lane.test.mjs.

**C52. A regression's history, bought once.** Trigger: `lane: 'fix'` with `regression: true`. Behavior: one `vf-agentics:historian` dispatch before planning, whose findings reach the planner and through it the coder. Search-shaped output, so `stop_reason` is an enum and `searched` carries the ground covered (IRON LAW §2), and the historian is told never to guess a commit — a sha nobody read sends the fix at code that was never the problem. IRON LAW §5: the channel has its `.catch`, a failure leaves the lane exactly where it was, `history` lands in `failed_channels`, and `unreached` says the introducing commit was never identified so a claim resting on it is visibly unsupported. The flag is the caller's rather than inferred from the change string, and is cheap wrong in both directions: a missed regression costs one search a coder can still do, a needless one costs a single read-only dispatch. An ordinary fix buys none, because there is no such commit to find. Source: workflow.js `HISTORY` / `historianPrompt` / the fix-lane history block; test/vfa-develop-fix-lane.test.mjs.

**C53. What the fix lane refuses to make cheap.** Trigger: any fix-lane order reaching verification or review. Behavior: nothing is dropped but the two phases named in C50. The discriminator still proves the test fails without the fix and still routes through `discriminator_undecidable` when it is the only failing fact; the adversarial reviewer still attacks the series and its criticals still hold the order; the mechanical checks run whole — commit series, build, typecheck, suite; the integration review still reads the merged head. `coverage.from_kb` states that the lane ran, that NOTHING was searched by this run, that nothing was recalled from the knowledge base either, and which locus was declared — a lane and a fresh KB chain must never read alike there, one being a caller's judgment that the ground is known and the other a program's finding that it is recorded. Source: workflow.js `fixLane` branch of `surveyCoverage`; test/vfa-develop-fix-lane.test.mjs.

## D. Run state & resume (.claude/vfa/runs/, lib/run-verdict.mjs, lib/ledger.mjs, lib/run-status.mjs)

**D1. Record authorship.** Trigger: any wave activity. Behavior: workflow decisions → state.jsonl ('wave'/'order-approved'/'order-escalated', workflow.js:1787-1825); agents journal their OWN observations in the execution that performed them (coder 'coder-done', verifier 'verify-observed', merger 'merge-observed') — closing the window where work exists and disk doesn't say so (0.14.0 postmortem: a wave's merges existed but the separate recorder courier was killed by the same limit; commit 5344f2b). One monotonic seq minted by the workflow spans both files (a counter, not a clock — an agent that can read a clock can fabricate one; commit c82a8ce, 0.15.0). lib/ledger.mjs appendLine is the sole physical writer and refuses any line whose digest doesn't recompute (:93). Agents never journal verdicts — verdicts are re-derived on resume.

**D2. Journal write refused.** Trigger: agent can't append. Behavior: degrade — stop_reason 'unwritable', "return your result anyway" (agents/verifier.md:115, run-state.md:69); appendState failures .catch-swallowed (workflow.js:1750).

**D3. Resume transport.** Trigger: develop re-invoked with resume_path. Behavior: survey/plan skipped (:2670-2677); one courier runs lib/run-verdict.mjs and pastes its stdout; workflow recomputes the payload digest before believing a word ("bytes never ride a model," increment-9-contracts.md:29); transport failure buys exactly one retry one model tier up (:2728-2772); both tiers failing → loud non-dispatching halt with resume_path (:2774-2793). Lineage: the haiku loader paraphrased 13 of 14 orders (0.9.1, commit 7b377d3), then the fan-out — no dispatch ever carries the whole plan, one courier per manifest row against its own digest (0.10.0, commit d5d947b).

**D4. Change guard.** Trigger: resume where the plan was written for a different change string. Behavior: halt before any dispatch. Source: workflow.js:2807-2825.

**D5. Clean-run fast path.** Trigger: resume of a run that recorded nothing. Behavior: empty ledger + no vfa/\<runstamp\>-* branches proven by one `git branch --list`, logged aloud so the skipped archaeology is visible. Source: lib/run-verdict.mjs:698; workflow.js:2829-2835.

**D6. Stage-wise salvage ladder.** Trigger: resume of a dirty run. Behavior: replay() folds both ledgers per order; nextActionFor() walks merge→review→verify→continue-series→code and trusts a stage only where the run record AND git's branch head agree; disagreement redoes the stage; rebuild ('code') is the ladder's bottom. Continue-series is offered only when the run demonstrably speaks the coder-done dialect (some other order recorded one) — a pre-0.14 run with commits resumes at verify, never continue (run-verdict.mjs:493-509). Source: run-verdict.mjs:51, 247, 451-509; commit 5abc24b (0.13.0).

**D7. Merge done, record lost.** Trigger: order branch is an ancestor of integration but no wave line recorded it. Behavior: ancestry alone is NEVER trusted (a coder that died before its first commit is also an ancestor — the empty-branch adversarial finding, increment-6-contracts.md:56-64); a second witness is required (approval head match or merge-observed journal line); reconciled orders get a corrective wave line and one verification of that head. Source: run-verdict.mjs:474-483; workflow.js:2872, :3710.

**D8. Corrupt run state.** Trigger: plan.json missing/unparseable or verdict damaged beyond retry. Behavior: corruptHalt — failed_channels:['run-state'], nothing dispatched, and pointedly never "every order coupled" (a documented field failure that offered four merged orders back for reimplementation). **D9. Uncommitted work.** Trigger: dirty worktree found on resume. Behavior: reported via git status --porcelain, never adopted automatically; commits are the unit of salvage. Source: run-verdict.mjs:759; proposal-deterministic-ledger-resume:203.

**D10. Concurrent runs / existing worktree / pruned worktree.** Trigger: multiple runs in flight, or resume finds its branch/worktree already present or pruned. **D11. Envelope adoption.** Trigger: resume with caller-supplied conditions. Behavior: roots/intelligence/programme/slice/base adopted from the plan on disk, overrides logged; only 'change' must match or halt. Source: workflow.js:2955; proposal-run-lifecycle:131.

**D12. A ledger line too long for a command line.** Trigger: a state line whose base64 token exceeds the platform's command-line limit — Windows caps a process's at 8191 characters, and a wave line carries every id its wave touched plus everything its coders discovered. Behavior: `lib/ledger.mjs append` gains `--b64-file`, the escape hatch `lib/kb.mjs` already had for the same reason and the same run: the token is written to a file in pieces and the PATH is passed, which is short whatever the line weighs and reaches the process without crossing a model. `--b64` stays for small lines and for every caller already written against it; the file wins when both are given, being the one that cannot have been truncated on the way in; an unreadable file is refused by name rather than read as an empty line. The recorder prompt and `agents/run-state.md` carry the fallback, phrased as the KB path already phrases it — a heredoc and a script file are NOT alternatives, because they put the same token on the same one command line. Source: lib/ledger.mjs `lineBytes`; workflow.js `recorderPrompt`; agents/run-state.md; test/ledger.test.mjs.

**D13. A refused ledger write, retried once.** Trigger: a recorder returning `stop_reason: 'unwritable'` — the writer saying it checked the digest and appended nothing. Behavior: one fresh recorder gets the same line, under the label `<label>:retry`. A refusal is a fact that nothing was written, so a second dispatch cannot duplicate a line; a throw or a null return leaves the outcome unobserved and is NOT retried, because a retry there could append twice. Exactly one retry: a loop here would never end. Alongside it, the digest is minted over the line as the writer will see it — after the JSON round trip — because `JSON.stringify` drops an undefined-valued key while `canonical` writes it as null, so digesting the object as BUILT mints a number the writer cannot reproduce over the very bytes it was sent, and refuses a line nobody mistyped. Field case: run `20260902-124933` lost seven genuine merges from `state.jsonl` to a single refusal with no second attempt, leaving the next resume to re-derive them from git. Source: workflow.js `appendState`; test/vfa-develop-resilience.test.mjs.

**D14. A failed channel, said out loud.** Trigger: any invocation ending with a non-empty `failed_channels`. Behavior: each channel also reaches `coverage.unreached` as a sentence naming what it costs — a run-state channel that failed means a resume must re-derive outcomes from git and may redo work that already landed; a kb channel that failed means the next run pays again to learn what this one learned. `complete` is untouched, because the run did the work and what failed is the record of it. The reason is legibility rather than arithmetic: `failed_channels` is a list of bare words beside a list of sentences, and both channels that fail without failing the run cost the NEXT invocation rather than this one — the kind of damage nothing downstream detects and nobody reads past a word list to find. Field case: in run `20260902-124933` a lost ledger write and a failed kb channel both appeared only there. Source: workflow.js `CHANNEL_COST` / `channelNote` / `coverageOf`; test/vfa-develop-resilience.test.mjs.
